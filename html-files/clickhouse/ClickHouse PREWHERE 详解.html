ClickHouse 查询优化系列

PREWHERE 详解

深入理解 ClickHouse 中「先过滤、后读列」的查询优化机制，通过大量示例掌握 PREWHERE 的原理、用法与最佳实践。

🧩一、什么是 PREWHERE

PREWHERE 是 ClickHouse 中用于优化查询的一种机制，它属于 MergeTree 表引擎家族的特性。核心思想是：在读取其他列的数据之前，先用过滤条件把大部分不相关的行「筛掉」，从而大幅减少磁盘 I/O 与内存开销。

在传统的 SQL 执行流程中，数据库会先读取查询涉及的所有列，再统一执行 WHERE 过滤。而 ClickHouse 的 PREWHERE 改变了这个顺序：先只读取过滤条件涉及的列，完成过滤得到「幸存行」的位置，再按位置读取 SELECT 真正需要的列。

一句话理解

PREWHERE 就是「先拿筛子把大米筛一遍，再只捡筛出来的米粒去称重」，而不是把整袋米都倒出来称完再挑。

💡二、为什么需要 PREWHERE

要理解 PREWHERE 的价值，首先要理解 ClickHouse 的列式存储特点：数据按列而不是按行存储在磁盘上，每一列是一个独立的文件。

假设有一张 50 列、1000 万行的宽表，执行下面的查询：

SQLSELECT user_id, url, duration FROM user_events WHERE event_type = 'purchase';

这条查询实际涉及 4 列：user_id、url、duration（SELECT 需要）以及 event_type（WHERE 需要）。

没有 PREWHERE 时的问题

传统 WHERE 的执行方式：先把 4 列的全部 1000 万行数据都读进内存，然后才做过滤。即使最终只有 1% 的行（10 万行）满足条件，另外 99% 的数据也被白白读了一遍，造成巨大的 I/O 浪费。

PREWHERE 的解决思路

使用 PREWHERE 后：先只读取 event_type 这一列的全部数据（1000 万行，但只有 1 列），过滤后只剩 10 万行幸存，再按这 10 万行的位置去读取 user_id、url、duration 三列的数据。

普通 WHERE 读取量 = 4 列 × 1000 万行
PREWHERE 读取量 = 1 列 × 1000 万行 + 3 列 × 10 万行

列数越多、过滤率越高（幸存行越少），PREWHERE 的收益就越明显。这正是宽表分析场景中 PREWHERE 能带来「数量级」性能提升的原因。

⚖️三、PREWHERE 与 WHERE 的区别

两者在语义上完全等价（返回的结果集一模一样），区别只在于执行顺序与读取策略。PREWHERE 是 WHERE 的优化版本，而不是替代品。

注意

PREWHERE 不是「更严格的过滤」，它只是改变了读取顺序。如果过滤条件列恰好也是 SELECT 需要的列（例如 SELECT event_type ... WHERE event_type = 'purchase'），那么 PREWHERE 的收益会大打折扣，因为过滤列本身最终也要被完整读取。

⚙️四、PREWHERE 的工作原理

在 MergeTree 表引擎中，数据按列存储，每列是一个独立文件，且按主键排序。PREWHERE 的底层执行过程可以拆解为以下步骤：

定位数据部分（Part）：根据主键索引与分区裁剪，确定需要扫描的 data part 集合。
只读取过滤列：从磁盘加载 WHERE 条件涉及的列（如 event_type）的压缩数据块。
向量化过滤：利用 SIMD 向量化引擎对整列数据做条件判断，生成一个布尔掩码（mask），标记哪些行满足条件。
得到幸存行位置：根据掩码计算出幸存行在数据块中的行号偏移集合。
按位读取目标列：只从磁盘读取幸存行对应的 user_id、url、duration 等列的数据块。
组装结果：将过滤列与目标列按行号对齐，输出最终结果。
关键点

PREWHERE 的收益来自「减少目标列的读取量」。过滤列本身仍然要读全部行，但通常过滤列只有 1~2 列，而目标列可能有几十列，因此整体 I/O 大幅下降。

📝五、详细示例

5.1 准备测试表

先创建一张宽表并插入模拟数据：

SQLCREATE TABLE user_events ( user_id UInt32, event_date Date, event_type String, url String, device String, duration UInt32, city String, ip String, -- ... 假设共有 50 列 extra_50 String ) ENGINE = MergeTree ORDER BY (event_date, user_id); -- 插入 1000 万行模拟数据（其中约 1% 为 purchase 事件） INSERT INTO user_events SELECT rand() % 1000000, today() - rand() % 365, if(rand() % 100 < 1, 'purchase', 'view'), concat('/page/', toString(rand() % 1000)), 'mobile', rand() % 300, 'Beijing', concat(toString(rand() % 255), '.', toString(rand() % 255)), 'x' FROM numbers(10000000);

5.2 示例一：显式使用 PREWHERE

在 WHERE 之前用 PREWHERE 关键字显式声明过滤条件：

SQLSELECT user_id, url, duration FROM user_events PREWHERE event_type = 'purchase' -- 先过滤 WHERE event_date >= '2024-01-01'; -- 其余条件放 WHERE

执行时，ClickHouse 会先读取 event_type 列完成过滤，再按幸存行读取 user_id、url、duration，最后在内存中对 event_date 做二次过滤。

5.3 示例二：隐式自动优化（推荐）

从 ClickHouse 5.0 开始，optimize_move_to_prewhere 默认开启。即使不写 PREWHERE，ClickHouse 也会自动把合适的 WHERE 条件下推到 PREWHERE 阶段：

SQLSELECT user_id, url, duration FROM user_events WHERE event_type = 'purchase'; -- 无需手动写 PREWHERE

ClickHouse 的优化器会自动分析：event_type 是过滤列且不在 SELECT 中，适合下推，于是自动生成 PREWHERE 执行计划。

5.4 示例三：EXPLAIN 验证是否命中 PREWHERE

使用 EXPLAIN 查看执行计划，确认优化是否生效：

SQLEXPLAIN SELECT user_id, url, duration FROM user_events WHERE event_type = 'purchase';
输出┌─explain─────────────────────────────────────────┐ │ Expression │ │ ReadFromMergeTree │ │ Prewhere: event_type = 'purchase' ← 已下推 │ Columns: user_id, url, duration │ Parts: 12 / 12 │ Granules: 1562 / 1562 └───────────────────────────────────────────────┘

执行计划中出现 Prewhere 一行，就说明自动优化已生效。

5.5 示例四：多条件组合

多个过滤条件时，ClickHouse 会选择过滤率最高（选择性最强）的条件下推到 PREWHERE：

SQLSELECT user_id, city, duration FROM user_events WHERE event_type = 'purchase' AND city = 'Beijing' AND duration > 120;

优化器会评估各条件的过滤能力，通常将 event_type = 'purchase'（过滤掉 99% 数据）下推到 PREWHERE，其余条件留在 WHERE 阶段处理。

5.6 示例五：关闭自动优化

如果希望完全手动控制，可以关闭自动下推：

SQLSET optimize_move_to_prewhere = 0; -- 关闭自动下推 SELECT user_id, url FROM user_events WHERE event_type = 'purchase'; -- 此时走普通 WHERE

也可以对单条查询使用 SETTINGS 控制：

SQLSELECT user_id, url FROM user_events WHERE event_type = 'purchase' SETTINGS optimize_move_to_prewhere = 0;

🤖六、自动优化机制

ClickHouse 的优化器会自动判断哪些 WHERE 条件适合下推到 PREWHERE。了解这些规则，有助于写出能被自动优化的查询。

适合自动下推的情况

  • 过滤列不在 SELECT 中：过滤列只用于判断，不需要输出，下推收益最大。
  • 过滤率高：能过滤掉大部分行，幸存行越少收益越大。
  • 表是宽表：列数越多，避免读取的列就越多。
  • 简单表达式：如 col = value、col IN (...)、范围比较等。

不会自动下推的情况

场景 原因
涉及 ALIAS 列 别名列依赖其他列的值，无法提前计算
常量表达式 如 WHERE 1 = 1，无需下推
表列数很少 如只有 2~3 列，下推收益几乎为零，甚至更慢
过滤列就是 SELECT 列 该列反正要读全量，下推无意义
某些复杂函数 依赖多列或无法向量化的表达式
经验法则

当表只有 2~3 列时，PREWHERE 反而可能带来额外开销（多一次列读取调度）。窄表不要用 PREWHERE，宽表 + 高过滤率才是它的主场。

📊七、性能对比分析

以「50 列宽表、1000 万行、过滤后剩 10 万行」为例，量化对比两种方式的磁盘读取量：

指标 普通 WHERE PREWHERE 节省
过滤列读取 1 列 × 1000 万行 1 列 × 1000 万行 —
目标列读取 3 列 × 1000 万行 3 列 × 10 万行 减少 99%
总读取行数 4000 万行 1030 万行 减少约 74%
I/O 开销 高 低 显著降低

过滤率越高，收益越明显：

  • 过滤率 99%（幸存 1%）：目标列读取量减少 99%，收益巨大。
  • 过滤率 50%（幸存 50%）：目标列读取量减半，收益中等。
  • 过滤率很低（幸存 90%+）：PREWHERE 额外增加一次过滤列读取调度，收益可能为负。
实测参考

在典型的宽表分析场景中，PREWHERE 通常能带来 2~10 倍的查询加速；配合主键索引、跳数索引使用时，效果可以进一步叠加。

⚠️八、使用限制与注意事项

  • 仅 MergeTree 家族支持：PREWHERE 只适用于 MergeTree、ReplacingMergeTree、SummingMergeTree、AggregatingMergeTree 等表引擎，普通内存表、Kafka 表等不支持。
  • 与 FINAL 的关系：使用 FINAL 时，PREWHERE 条件可能无法完全下推，ClickHouse 会自行处理。
  • 与 SAMPLE 的关系：采样查询（SAMPLE）与 PREWHERE 可以共存，但执行顺序由优化器决定。
  • 过滤列在 SELECT 中：如果过滤列也要输出，PREWHERE 收益会明显下降。
  • 不要过度手动指定：现代版本默认自动优化，手动写 PREWHERE 主要用于强制指定或调试。
  • 结合索引使用：PREWHERE 是「减少列读取量」的优化，与主键索引（减少数据块扫描量）、跳数索引（跳过数据块）是不同维度的优化，可叠加使用。

🏆九、最佳实践与总结

最佳实践

  1. 优先依赖自动优化：保持默认的 optimize_move_to_prewhere = 1，让优化器自动决策。
  2. 宽表 + 高过滤率场景显式指定：当确认过滤条件选择性极强（如状态字段、事件类型）时，可显式写 PREWHERE 明确意图。
  3. 用 EXPLAIN 验证：上线前用 EXPLAIN 确认执行计划中是否出现 Prewhere。
  4. 窄表不要用：列数很少时，PREWHERE 收益为负，交给优化器即可。
  5. 与索引协同：把高过滤率字段同时纳入主键或跳数索引，与 PREWHERE 形成「索引裁剪 + 列裁剪」双重优化。

总结一句话

PREWHERE 是 ClickHouse 针对列式存储设计的「过滤前置」优化：先用少数过滤列筛掉大部分行，再按幸存行读取目标列，从而大幅减少磁盘 I/O。宽表 + 高过滤率时收益显著，现代版本默认自动开启，是 ClickHouse 查询性能优化中最常用也最容易被忽视的利器之一。
