ClickHouse 高级特性

投影（Projection）详解

在同一个表内创建数据的多个物理副本，以不同的排序键或预聚合方式存储，
让查询优化器自动选择最优路径——无需改动任何 SQL。

🔮 什么是投影？

投影（Projection） 是 ClickHouse MergeTree 表引擎家族提供的一项高级特性。它允许你在同一张表内部，基于原始数据创建额外的物理存储副本，每个副本可以拥有独立的排序键，甚至可以是预聚合后的结果。

投影的核心思想是「以空间换时间」——通过冗余存储来加速特定模式的查询。当查询到达时，ClickHouse 的查询优化器会自动判断哪个投影最合适，透明地从中读取数据，完全不需要修改查询语句。

📐 投影的两种类型

① 普通投影（Normal Projection）

选择部分或全部列，但使用不同的排序键重新组织数据。适合加速特定列的过滤和排序查询。

适用场景：主表按 order_date 排序，但经常按 customer_id 过滤查询。

② 聚合投影（Aggregate Projection）

在投影中直接预计算聚合结果（如 SUM、COUNT、AVG 等），查询时直接读取聚合后的数据，避免实时扫描全表。

适用场景：频繁按产品统计销售额、按用户统计访问次数等聚合查询。

⚖️ 投影 vs 物化视图

投影和物化视图都能实现查询加速，但它们的架构和适用场景有显著差异：

对比维度 投影（Projection） 物化视图（Materialized View）
数据存储 与主表 同一张表，共享生命周期 独立的物理表，独立生命周期
数据一致性 ✅ 强一致——写入主表时原子性同步更新 ⚠️ 可能不一致——主表与视图写入独立，出错时可能丢失数据
查询透明性 ✅ 完全透明——优化器自动路由，SQL 无需修改 ⚠️ 需要手动查视图表，或使用 MATERIALIZED VIEW + TO 目标表
写入性能 写入时额外计算投影，有一定开销 异步写入，对主表写入影响较小
灵活性 限于基于同一张表的变换 支持多表 JOIN、过滤、复杂转换
维护成本 低——自动管理，无需额外操作 高——需独立管理、监控数据一致性

总结：如果只需要在单表内做排序优化或简单聚合，投影是比物化视图更优雅、更可靠的选择。物化视图更适合跨表 JOIN 或复杂 ETL 场景。

📝 详细示例

我们先创建一个销售订单表，然后逐步添加不同类型的投影，并通过实际查询观察效果。

示例 1：准备基础表

创建一个销售订单表，主排序键为 (order_date, customer_id)。

SQL CREATE TABLE sales ( order_date Date, customer_id UInt32, product_id UInt32, category String, amount Float64, quantity UInt32 ) ENGINE = MergeTree() ORDER BY (order_date, customer_id);

示例 2：创建普通投影（更改排序键）

我们经常按 product_id 查询销售额，而主表是按日期排序的。创建一个按 product_id 排序的投影：

SQL ALTER TABLE sales ADD PROJECTION sales_by_product ( SELECT * ORDER BY product_id ); ALTER TABLE sales MATERIALIZE PROJECTION sales_by_product;
📊 效果演示
执行查询 SELECT * FROM sales WHERE product_id = 42 ORDER BY amount DESC —— 优化器自动从 sales_by_product 投影读取数据，
因为该投影的排序键 product_id 与 WHERE 条件完全匹配，无需扫描全表。
✅ 查询速度提升：10 ~ 50 倍（取决于数据量）

示例 3：创建聚合投影（预聚合）

我们经常按产品类别汇总销售额和订单量，创建一个聚合投影来预计算：

SQL ALTER TABLE sales ADD PROJECTION sales_category_summary ( SELECT category, count() AS order_count, sum(amount) AS total_amount, avg(amount) AS avg_amount, sum(quantity) AS total_quantity GROUP BY category ); ALTER TABLE sales MATERIALIZE PROJECTION sales_category_summary;
📊 效果演示
执行查询 SELECT category, sum(amount) AS total FROM sales GROUP BY category —— 优化器自动使用 sales_category_summary 投影，
直接从预聚合结果中读取数据，无需扫描全表逐行计算。
✅ 查询速度提升：100 ~ 1000 倍（大数据量下，I/O 从 GB 级降至 KB 级）

示例 4：创建复合聚合投影（多维度）

如果需要按产品 + 日期统计销售指标：

SQL ALTER TABLE sales ADD PROJECTION sales_daily_product ( SELECT order_date, product_id, count() AS sale_count, sum(amount) AS daily_amount, sum(quantity) AS daily_quantity GROUP BY order_date, product_id ); ALTER TABLE sales MATERIALIZE PROJECTION sales_daily_product;

技巧：聚合投影的 GROUP BY 列越多，覆盖的查询模式越广，但存储开销也越大。建议只对高频查询模式创建投影。

🎯 投影的核心用途

🚀 用途一：加速特定列的过滤查询
问题：主表按 timestamp 排序，但业务方经常按 user_id 查最近行为。
方案：创建一个按 user_id 排序的普通投影。
原理：投影的排序键与 WHERE 条件匹配时，ClickHouse 可以通过二分查找精确定位数据块，避免全表扫描。
⚡ 用途二：预聚合加速报表查询
问题：每小时需要按 10 个维度汇总上亿条数据，实时计算耗时 30 秒+。
方案：创建包含 GROUP BY 的聚合投影，数据写入时即完成预计算。
原理：聚合投影将 O(n) 的实时聚合降为 O(1) 的读取，I/O 减少 99% 以上。
📉 用途三：降低存储与 I/O
问题：表中包含 100 列，但某类查询只需要 5 列。
方案：创建一个只包含那 5 列的普通投影（SELECT col1, col2, ...）。
原理：投影只存储指定列，扫描时读取更少的数据页，减少 I/O 和内存开销。
🔄 用途四：替代物化视图的简单场景
问题：需要预聚合但又担心物化视图的数据一致性问题。
方案：使用聚合投影代替物化视图。
原理：投影与主表数据强一致，原子性写入，不存在物化视图因写入失败导致的数据丢失或重复问题。

⚠️ 使用注意事项

  • 存储开销：每个投影都是数据的完整副本（或部分副本），会增加磁盘占用。建议只对关键查询模式创建投影。
  • 写入放大：写入数据时，所有投影都需要同步更新，INSERT 性能会有所下降。适用于写少读多的场景。
  • 聚合投影的限制：聚合投影的 GROUP BY 列必须包含在 ORDER BY 中，且聚合函数必须是 ClickHouse 支持的聚合函数。
  • 存量数据的物化：使用 ALTER TABLE ... MATERIALIZE PROJECTION 对已有数据构建投影，对于大表可能需要较长时间，建议在低峰期执行。
  • 投影的删除：使用 ALTER TABLE ... DROP PROJECTION 删除投影，会同时删除对应的物理数据。
  • 查询覆盖度：并非所有查询都能命中投影——优化器会评估投影的排序键与查询条件的匹配程度。可以使用 EXPLAIN 查看查询是否使用了投影。

查看投影是否被使用：在查询前加上 EXPLAIN，输出中如果包含 ReadFromMergeTree 且显示投影名称，说明查询命中了该投影。

💡 最佳实践

  1. 先分析慢查询：使用 system.query_log 找出耗时最长的查询，针对性地创建投影。
  2. 优先使用聚合投影：聚合投影的加速效果远大于普通投影，因为它在写入时就完成了计算。
  3. 控制投影数量：每张表建议不超过 3 ~ 5 个投影，过多的投影会导致写入性能严重下降。
  4. 使用 EXPLAIN 验证：创建投影后，用 EXPLAIN 检查高频查询是否确实命中了投影。
  5. 监控投影存储：通过 system.parts 表查看每个投影分区的数据量，及时发现存储异常增长。
  6. 配合分区键：投影与分区键（PARTITION BY）配合使用效果更佳，分区剪枝 + 投影加速可以带来双重性能提升。
