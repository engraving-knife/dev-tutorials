01

YARN 是什么：定位与设计动机

YARN（Yet Another Resource Negotiator）是 Hadoop 2.x 引入的通用资源管理系统，将原本耦合在 MapReduce JobTracker 中的「资源管理」与「作业调度」彻底拆分，成为 Spark、Flink、Tez 等所有计算框架共享的底层调度平台。

为什么需要 YARN？

在 Hadoop 1.x 中，JobTracker 同时承担资源管理和作业调度两大职责：它既要管理集群中所有节点的资源，又要负责任务的分发、心跳与容错。这带来三个致命问题：

  • 单点瓶颈：JobTracker 需要维护集群全部节点和作业的状态，集群规模超过 4000 节点后吞吐严重下降，成为扩展的天花板。
  • 耦合过深：调度逻辑与 MapReduce 计算逻辑绑死，其它计算框架（Spark、Flink…）无法复用这套资源管理能力。
  • 内存假设僵化：1.x 按「槽位（Slot）」划分 Map/Reduce 固定资源，无法表达真实的内存需求，浪费严重。

YARN 的三大设计思想

思想一

调度与计算解耦

RM 只负责「分资源」，不关心作业内部怎么跑；作业的计算逻辑完全交给每个应用自己的 ApplicationMaster。

思想二

统一的资源抽象 Container

把 CPU、内存等资源封装为「容器（Container）」这一标准单位，任何框架都以 Container 为单位申请与使用资源。

思想三

框架化 ApplicationMaster

每个应用由自己的 AM 负责任务级调度、失败重试、进度汇报，框架可自由实现，YARN 只提供通用 API。

这一模型让同一套集群可以同时承载 MapReduce、Spark、Flink、Tez、HBase 等不同类型的作业，真正实现「一个集群、多框架共存」。

YARN 采用经典的「全局管理者 + 节点管理者 + 应用代表 + 资源容器」四层模型。理解这四个角色，就掌握了 YARN 的主从架构骨架。

ResourceManager（RM）

集群中唯一、全局的资源调度中枢，负责统筹整个集群的 CPU / 内存等资源。它内部由两个核心组件构成：

  • Scheduler（调度器）：纯粹的「资源分配器」，只维护队列、容量与节点资源视图，把 Container 分配给等待中的作业，不关心任何作业内部逻辑。
  • ApplicationsManager（ASM）：应用生命周期管理者，负责接收作业提交、校验队列与 ACL、为应用分配首个 Container 并命令 NodeManager 启动 ApplicationMaster，同时监控 AM 心跳，超时则判定 AM 失败并重启。

NodeManager（NM）

运行在每个节点上的「节点资源管家」，是资源使用的执行末端：

  • 周期性（默认 1s）向 RM 心跳，上报本节点可用资源、运行中的容器与健康状态。
  • 通过 ContainerExecutor（默认 LinuxContainerExecutor + cgroups）真正启动、停止容器进程，并施加资源限制。
  • 持续监控每个容器的物理内存、虚拟内存与 CPU 使用，超限即 kill 容器，防止「内存炸弹」拖垮节点。
  • 承担日志聚合、磁盘健康检查，以及 MapReduce Shuffle 等辅助服务。

ApplicationMaster（AM）

每个应用一个「作业的代言人」，由计算框架自己实现：

  • 启动后向 RM 注册并周期性心跳（默认超时 10 分钟判定 AM 失败）。
  • 把作业切分为任务（Task），构建资源请求（位置偏好、容器大小、优先级）提交给调度器。
  • 拿到分配的 Container 后，通过 ContainerManagerProtocol 请求对应 NM 启动任务容器。
  • 负责任务级调度、进度聚合、失败任务重试与整个作业的完成判定。

举例 MapReduce 作业的 MRAppMaster、Spark 的 Driver、Flink 的 JobManager 均以 AM 形式运行在 YARN 上。

Container（容器）

YARN 中最核心的资源抽象单位，一个 Container 代表：

  • 一组资源：内存（MB）+ vCore（虚拟 CPU 核），可扩展 GPU 等异构资源。
  • 一个受限进程：NM 以独立进程 + cgroups 限制启动，互不干扰。
  • 一个执行上下文：包含启动命令、环境变量、依赖 jar、日志目录等。

关键点：Container 不是由 RM 直接启动，而是 RM「分配许可」、AM「申请启动」、NM「真正拉起」。首尾两个特殊容器分别承载 AM 与任务进程。

03

资源调度机制

调度是 YARN 的心脏。Scheduler 接收各 AM 的资源请求，结合队列容量与节点资源视图，决定「谁、在哪个节点、拿多大的容器」。默认资源维度为 内存（MB）与 vCore 两种。

FIFO Scheduler

最简 · 不推荐生产

先进先出，队列头部的作业独占全部可用资源，其余作业阻塞等待。

  • 优点：实现极简，无配置负担。
  • 缺点：队头阻塞——大作业压队时，后续小作业全部饿死，响应性差。

Capacity Scheduler

Hadoop 默认 · 生产首选

多队列，每个队列有保证容量（guaranteed capacity）；队列占用未满时，其余队列可弹性借用其空闲容量，并用 maximum-capacity 限制借用上限。

  • 队列内支持 FIFO / 优先级 / 严格公平（ordering-policy）。
  • 容量保证 + 弹性共享，天然适合多团队多租户生产集群。

Fair Scheduler

多作业公平 · 支持抢占

所有运行中的作业公平共享资源（支持 weight 加权、min/max share）。资源不足时按比例让各自作业获得近似等量资源。

  • 短作业启动快、延迟低，作业间相互影响小。
  • 支持基于 min share 的抢占（Preemption），回收超用资源。

资源请求与调度粒度

AM 每轮心跳会携带一批资源请求（ContainerRequest），调度器按「本地性偏好 → 队列配额 → 节点剩余资源」逐项匹配：

  • 请求内容：所需的资源量（内存 + vCore）、位置偏好（节点列表 / 机架 / ANY）、优先级。
  • 分配下限：yarn.scheduler.minimum-allocation-mb（默认 1024MB）与 vcore 下限——调度以它为粒度切分资源。
  • 分配上限：yarn.scheduler.maximum-allocation-mb（默认 8192MB），限制单个容器能拿到的最大资源。
  • 数据本地性：node-local（同节点）＞ rack-local（同机架）＞ off-switch（跨机架），本地性越好，Shuffle 网络开销越小。
调度器本身是「纯分配器」：它不知道任务是什么，只做三件事——维护队列、维护节点资源视图、把 Container 交给出价最高的队列内作业。
04

队列机制：容量、权限与抢占

队列是 YARN 多租户管理的核心载体：用「容量 + 上限 + 权限」把集群切成互相隔离的逻辑泳道，让不同团队 / 业务 / 作业类型并行安全地共享一台集群。

队列层级结构

队列是严格的层级树，根为 root，只能向叶子队列提交作业：

root
├── prod          # 生产队列 40%
│   └── etl       # 离线数仓
│   └── streaming # 实时流作业
├── adhoc         # 即席查询 20%
└── dev           # 开发测试 40%（上限 30%）

容量语义：同一父队列下，所有子队列的 capacity 之和 = 100%；父队列容量等于其全部子队列之和。

关键属性与配置

capacity保证容量百分比，子队列和=100%
maximum-capacity弹性借用上限，防止挤占他人
user-limit-factor单用户最多占队列容量的倍数
acl_submit_applications谁可以提交作业到该队列
acl_administer_queue谁可以管理队列（kill 作业等）
stateRUNNING / STOPPED（停用拒绝提交）
ordering-policy队列内 fifo / fair / priority

容量弹性与抢占

弹性机制：当队列 A 的空闲容量被队列 B 借用后，A 一旦有新作业提交，调度器会优先归还这些容量（新容器分配到 A，B 的资源随之减少）。若 B 长期超用导致 A 无法满足保证容量，则触发抢占。

抢占策略（Capacity Scheduler 通过调度监控器实现）：

yarn.resourcemanager.scheduler.monitor.enable   = true
yarn.resourcemanager.scheduler.monitor.policies = org.apache.hadoop.yarn.server.resourcemanager.monitor.capacity.ProportionalCapacityPreemptionPolicy

抢占器按「队列保证容量缺口」回收被超用容器（优先抢占最超用队列中、生命周期较短的容器），保证各队列的 SLA。注意：抢占是「杀容器」级别的强回收，会打断正在运行的任务，需结合 maximum-capacity 与合理容量规划共同使用。

经验：生产上通常为「低优先级批处理」队列设置偏小的 capacity 与严格 maximum-capacity，为「核心业务」队列保留足够保证容量，抢占应作为兜底而非常态。
05

资源隔离：内存、CPU 与 cgroups

资源隔离保证「一个作业的容器异常，不影响同节点其它作业」。YARN 的隔离分为两层：逻辑限制（调度约束 + 监控强杀）与操作系统级隔离（cgroups）。

内存隔离

监控 + 强杀

  • NM 持续监控每个容器的物理内存（pmem）与虚拟内存（vmem）。
  • 超限判定：物理内存超过申请的容器内存，或虚拟内存超过 内存 × yarn.nodemanager.vmem-pmem-ratio（默认 2.1）。
  • 超限后 NM 直接 kill 容器并记录日志，防止拖垮节点。

CPU 隔离

cgroups 配额

  • vCore 是逻辑概念：节点可分配核数由 yarn.nodemanager.resource.cpu-vcores 决定。
  • LinuxContainerExecutor + cgroups 将每个容器放入独立 cgroup，用 cpu.shares（权重）与 cpu.cfs_quota_us / cpu.cfs_period_us（硬配额）真正限制 CPU 占用。
  • Hadoop 3.x 默认启用 cgroups v2，实现精确的 CPU 限额。

其它维度隔离

磁盘 · 网络 · 进程树

  • 磁盘：磁盘健康检查器监控每块盘使用率（默认 >90% 判坏），坏盘节点从调度中剔除。
  • 进程树：容器以独立进程组启动，kill 容器时连同子进程一并终止。
  • 网络：Hadoop 3.x 支持基于 cgroup 的带宽限制（tc）与资源类型扩展（GPU 等）。

节点资源上报与超卖风险

节点可用资源由 NM 上报，是全集群调度的基础：

yarn.nodemanager.resource.memory-mb  = 65536   # 上报给 RM 的内存（通常为机器内存的 90% 左右）
yarn.nodemanager.resource.cpu-vcores = 32      # 上报给 RM 的虚拟核数
yarn.nodemanager.container-executor.class = org.apache.hadoop.yarn.server.nodemanager.LinuxContainerExecutor

超卖警示：若节点上所有容器内存之和（含系统与 shuffle 服务开销）超过物理内存，就会出现「调度能分配、运行就 OOM」的假死现象。容器申请的内存应小于节点上报内存，且每个容器都要预留 JVM overhead；不建议通过调大 vmem-pmem-ratio 掩盖问题。

经验：节点上报内存 = 物理内存 × 0.9 − shuffle/系统预留；上报核数建议 ≈ 物理核数（可 nproc 查看）。隔离做得好，同节点混跑流批作业才安全。
06

任务提交流程全链路

一次作业提交，历经「Client → RM → NM → AM → Container」五个角色的接力。下面以 MapReduce 作业为例，梳理完整链路。

STEP 01
Client 提交作业到 RM

客户端通过 ApplicationClientProtocol 向 RM 的 ApplicationsManager 提交 ApplicationSubmissionContext：包含目标队列、AM 所需的容器规格、依赖资源、ACL 等。

STEP 02
RM 校验并分配「AM 容器」

RM 校验队列是否存在、提交权限、资源是否可满足。通过后生成 ApplicationId，Scheduler 分配第一个 Container（AM Container）并指定启动节点。

STEP 03
RM 命令 NM 启动 ApplicationMaster

RM 通过 ResourceTracker 协议向目标 NM 下发「启动 AM」指令；NM 用 ContainerExecutor 以受限进程拉起 MRAppMaster。

STEP 04
AM 注册并解析作业

AM 启动后向 RM 注册（host:port、tracking URL），随后周期性心跳。同时解析作业：读取 InputSplit 切分 Map 任务，构建资源请求（位置偏好 + 内存/核数 + 优先级）。

STEP 05
AM 向调度器申请资源

AM 在每个心跳周期把资源请求带给 Scheduler；Scheduler 结合队列容量、节点资源视图与本地性偏好分配 Container，返回 ContainerId + ContainerToken。

STEP 06
AM 请求 NM 启动任务容器

AM 通过 ContainerManagerProtocol（startContainer）向对应 NM 下发启动上下文：命令、环境变量、日志目录。NM 启动容器进程运行 Map / Reduce 任务。

STEP 07
任务运行、监控与重试

NM 监控容器资源并上报状态；AM 聚合任务进度，失败任务自动重试（MapReduce 默认单任务 4 次），并维护黑名单节点。

STEP 08
作业完成与资源回收

全部任务结束，AM 向 RM 注销并报告最终状态；RM 清理应用记录，回收所有 Container，Client 拿到结果。

协议速记

协议通信双方职责
ApplicationClientProtocolClient ↔ RM提交作业、查询进度、kill 应用
ApplicationMasterProtocolAM ↔ RM注册、心跳、申请 / 释放资源
ResourceTrackerProtocolNM ↔ RM节点心跳、上报资源与容器状态
ContainerManagerProtocolAM ↔ NM启动 / 停止容器、获取容器状态
07

容器生命周期管理

Container 是 YARN 中资源的最小管理单元，其生命周期由「RM 分配 → AM 申请 → NM 启动 → 运行监控 → 结束回收」驱动。

容器状态流转

NEW 已分配
⟶
RUNNING 运行中
⟶
COMPLETE 结束
COMPLETE 按退出码细分：0 = 正常完成 · 非 0 = 任务失败 · 被 kill / 抢占 / OOM = 异常终止
  • NEW：Scheduler 已把资源许可分给作业（携带 ContainerToken），但容器进程尚未启动。
  • RUNNING：NM 已用 ContainerExecutor 拉起容器进程并施加资源限制；NM 持续监控内存/CPU，超限即强杀。
  • COMPLETE：任务自然结束（exit 0）、失败（exit 非 0）、被抢占回收，或被 NM / RM / AM 主动 kill。

两类容器，两种容错

  • AM 容器：承载 ApplicationMaster。AM 心跳超时（默认 10 分钟）或异常退出，RM 判定该次 attempt 失败，重新分配 AM 容器重启（attempt 递增，受 yarn.resourcemanager.am.max-attempts 与 am.max-attempts 限制）。
  • 任务容器：承载具体 Task。由 AM 负责监控与重试（如 MapReduce 默认重试 4 次），超过阈值则将节点加入黑名单，向调度器申请其它节点的容器继续执行。

容器的三种终止路径

  • 正常完成：任务进程 exit 0，NM 回收资源并上报，AM 归还 Container。
  • 失败：任务 exit 非 0 或资源超限被 NM 强杀（常见退出码：137 = OOM，143 = 被 kill）；由 AM 重试或失败整个作业。
  • 抢占 / 主动回收：调度器抢占策略、节点优雅下线（Decommissioning）、管理员 kill 或 RM 故障切换导致容器被回收。

内存超限判定逻辑

物理内存 pmem 超出容器申请内存 → 判定超限
虚拟内存 vmem 超出 申请内存 × vmem-pmem-ratio(默认2.1) → 判定超限
超限 → NM 强杀容器，退出码 137（OOM kill）

因此排查「容器反复被杀」时，第一眼要看：退出码、NM 日志、容器日志中的内存曲线，判断是申请内存不足，还是代码内存泄漏。

08

生产实践经验：调优与排障

架构是骨架，实践才是血肉。以下经验来自多套生产集群的沉淀，覆盖选型、参数、排查与运维。

🎯 调度器与队列选型

  • 多团队 / 多业务共享集群 → Capacity Scheduler（Hadoop 默认，容量可控、隔离清晰）。
  • 作业类型混杂、短作业多、强调公平 → Fair Scheduler。
  • 队列按「业务 + 负载类型」分层：prod/etl、prod/streaming、adhoc、dev，核心业务保留保证容量，开发队列严格限制 maximum-capacity 与用户数。
  • 用 acl_submit_applications 收敛提交权限，防止测试作业挤占生产。

参数默认调优建议

yarn.scheduler.minimum-allocation-mb1024不宜过大，否则小作业浪费资源；512~1024 常用
yarn.scheduler.maximum-allocation-mb8192防止单容器过大造成碎片；按最大作业需求设置
yarn.nodemanager.vmem-pmem-ratio2.1JVM 堆外内存 / native 库常需调大至 3~4
yarn.resourcemanager.am.max-attempts2关键作业可调大，容忍节点抖动
yarn.nodemanager.heartbeat.interval-ms1000超大规模集群可调大，降低 RM 压力

应用侧配合：Spark 需按 executor-memory + overhead 申请容器内存；MapReduce 用 mapreduce.map.memory.mb / reduce.memory.mb 对齐容器规格。

🚑 高频故障排查

  • 作业一直 ACCEPTED / PENDING：队列容量不足、节点存在资源碎片（内存够但 vCore 不够，反之亦然）、本地性等待、AM 启动失败重试中。
  • 容器反复被杀：查退出码——137 = OOM（内存申请不足或泄漏）、143 = 被 kill（可能被抢占）。再配合 yarn logs -applicationId <id> 看容器日志。
  • 节点被剔除 / 失联：检查磁盘使用率（>90% 判坏）、NM 进程是否存活、网络与健康检查脚本。
  • 抢占频繁：队列保证容量规划不足，或生产队列缺少 maximum-capacity 兜底。
  • RM 变慢：心跳堆积、队列 pending 量大、RM JVM 堆不足（大集群建议 -Xmx 32G+）。

🧭 运维最佳实践清单

  • 开启日志聚合（yarn.log-aggregation-enable=true），集中排查；定期清理过期聚合日志。
  • 接入监控（Prometheus + YARN Metrics / Ganglia）：盯队列 Pending 数、节点已分配内存、NM 心跳延迟三个核心指标。
  • 流批混跑：不同负载分队列 + 优先级，必要时用节点标签（Node Label）做物理隔离。
  • 高可用：RM 部署双实例（RM HA + ZooKeeper），Master 故障秒级切换，作业由新 RM 自动恢复。
  • 升级注意：Hadoop 3.x 默认 cgroups v2、支持 GPU 资源类型（resource-types）、调度器性能大幅提升。
  • 容量规划遵循「保证 + 弹性 + 上限」三段式：保证核心业务，弹性利用空闲，上限保护弱者。
