01 · 身份与哲学

两种不同的湖上世界观

Iceberg 把自己定位成「开放表格式（metadata over files）」，Paimon 则把自己定位成「流式原生数据湖存储（introducing LSM-tree to the lake）」。定位之差，决定了后续几乎所有能力的分野。

Apache Iceberg

源自 Netflix，2020 年成为 Apache 顶级项目。以 metadata 树（metadata / snapshot / manifest list / manifest）为核心，把 Parquet、ORC 等数据文件组织成可事务化、可时间旅行、可被多引擎同时读写的大表。

对外观感近似「图书馆归档系统」：每次写入生成新快照，强调开放、中立、跨引擎兼容与数据治理。

多引擎快照治理开放格式批量分析成熟

Apache Paimon

起源于阿里 Flink Table Store，2024 年成为 Apache 顶级项目。把 LSM-tree、主键表、批量 compaction、原生 changelog 引入数据湖，让「表」更像一个流式数据库。

对外观感近似「超市生鲜货架」：新数据先入内存再刷盘排序，后台合并收敛，实时数据尽快可见，天然贴近 Flink 生态。

02 · 存储结构

元数据树 vs LSM-Tree：存储内核的分野

两者都基于对象存储 + 列式数据文件，但「如何管理文件、如何表达变更」的思路截然不同——这是本次对比最关键的工程差异。

Iceberg · Metadata Tree（元数据树）

<table_path>/
 ├─ metadata/
 │   ├─ version-hint.text      # 当前根元数据指针
 │   ├─ v2.metadata.json # 根元数据（schema/分区/snapshot history）
 │   ├─ snapshots/
 │   │   └─ snap-xxx.json
 │   ├─ manifest-lists/
 │   │   └─ snap-xxx-m.avro   # 一快照 → 一 manifest list
 │   └─ manifests/
 │       └─ uuid.avro          # 记录数据文件 + 列 min/max 统计
 └─ data/
     └─ xxx.parquet  （可按分区目录组织）
 v2/v3：delete files / Puffin deletion vector

核心思想：只描述「当前快照包含哪些文件」。快照之间复用 manifest，删除用 delete file / deletion vector（Roaring Bitmap）增量表达，读取时 merge。

Paimon · Bucket-LSM（分桶 LSM 树）

<table_path>/
 ├─ schema/      schema-0..n  # 表结构演进
 ├─ snapshot/    snapshot-1..n + LATEST
 ├─ manifest/    manifest-list / manifest-##
 ├─ tag/         tag-release_v1   # 命名快照，长期保留
 └─ dt=2026/                     # 分区层
     ├─ bucket-0/                 # 一棵独立 LSM 树
     │   ├─ sorted-run.parquet
     │   └─ changelog.parquet      # 变更日志
     └─ bucket-1/
         └─ ...

核心思想：主键表 每桶一棵 LSM-tree。新数据 → 内存 buffer → 按主键排序刷盘成 sorted run → 后台 compaction 合并收敛并处理更新/删除。

03 · 核心能力

写入、更新、并发：谁更能打？

一句话概括：追加与多引擎分析 Iceberg 更稳，高频更新与实时 CDC 场景 Paimon 更顺手。

写入路径

  • Iceberg：直接写 Parquet/ORC 并更新 manifest/metadata，追加与批量摄入稳定；高频更新依赖 MoR / deletion vector，写放大可控但需运维 delete 文件。
  • Paimon：先入内存 buffer → 排序刷盘成 sorted run → 后台 compaction 收敛，天然适合连续 UPSERT，毫秒到秒级可见。
  • 取舍：Paimon 需关注 compaction 资源与 bucket 调优；Iceberg 需关注 delete 累积与小文件治理。

读取路径

  • 批量分析：Iceberg 在 Trino / Spark / DuckDB 生态更成熟；Paimon 亦可，但深度略逊。
  • 实时流读：Paimon changelog 直接喂给下游 Flink 形成链式管道；Iceberg 需自行处理增量快照合并。
  • 点查：Paimon 的分桶 + LSM 对主键点查友好。

事务与并发

  • 两者都依赖「原子切换快照指针」获得 ACID 与快照隔离；支持时间旅行与回滚。
  • Paimon：并发写按 bucket 收敛，不同 bucket 可序列化，同 bucket 为快照隔离。
  • Iceberg：多 writer 通过 snapshot / metadata 提交协调，成熟度更高。

生态与治理

  • Iceberg：多引擎（Spark / Flink / Trino / Dremio / Snowflake…）、丰富治理工具与 AGPL/ASL 生态，跨团队共享与合规审计首选。
  • Paimon：Flink 集成为核心优势，跨引擎支持持续增强但广度、成熟度弱于 Iceberg。
04 · 适用场景

什么时候用 Paimon，什么时候用 Iceberg？

选型不是「谁更好」，而是「谁的模型匹配你的写入形态」。下面两个矩阵可直接对照你的场景。

优先选 Paimon

写入侧高变动 · 引擎侧重 Flink · 实时性要求高

  • 1CDC 实时入湖：MySQL / PG / Kafka 变更需秒级可见。
  • 2实时特征 / 风控：低延迟点查 + 高频更新。
  • 3主键表频繁 UPSERT：LSM 与 merge engine 天然承接。
  • 4Flink 流批一体：同一套任务读写流批数据。
  • 5实时聚合 / 物化视图：aggregation merge engine + changelog 链式消费。
  • 6实时报表看板：需流式数据持续刷新。

优先选 Iceberg

读取侧重分析 · 多引擎协作 · 低频更新 · 治理优先

  • 1多引擎协作：Spark / Trino / Dremio / DuckDB / Snowflake 混用。
  • 2PB 级离线分析：大规模 batch analytics 成熟场景。
  • 3合规与审计：时间旅行、快照保留、回滚能力强。
  • 4跨团队数据共享：开放格式生态与治理工具丰富。
  • 5Schema 频繁演进：field ID 机制 + 长期治理友好。
  • 6中低频更新：CoW / MoR / DV 处理，非高频 CDC。

混合架构 · Paimon + Iceberg 双湖

许多团队采用「双湖」：实时层用 Paimon 承接 CDC、实时特征与实时聚合；分析层用 Iceberg 沉淀历史与冷数据，服务多引擎分析与合规治理。热数据在实时层流动，冷数据在分析层沉淀，各取所长。

05 · 深度专题

TC Iceberg：腾讯云给 Iceberg 的「补强」

TC Iceberg 是腾讯云基于 Apache Iceberg 的非侵入式扩展，主要服务其 DLC（数据湖计算）与 TCLake 产品，兼容 Iceberg V1/V2 表格式。它的改进方向，恰好回应了 Iceberg 在「实时更新」上的短板——而不少设计思路与 Paimon 高度神似。

核心：Base Store + Change Store 双表

有主键表由两张独立 Iceberg 表组成：Base Store 存存量数据（Insert + Position Delete File），Change Store 专放实时增量（Flink 写入，可过期清理）。读取时 Merge-on-Read 合并两者提供分钟级分析。

这相当于用两张表「近似模拟」了 Paimon 的 LSM 分层思路——把新写入与存量分离、后台合并。

CDC 流式消费

增量数据以 append 写入 Change Store，支持流式增量读取，解决了标准 Iceberg「更新数据难以在下游流式消费」的问题——功能上对齐 Paimon 的原生 changelog。

自动分桶加速合并

写入时按主键 Hash 分桶，仅同桶内的 Change 与 Base 数据合并，减少 merge 时 shuffle 开销——思路与 Paimon 的 bucket + LSM 分区合并异曲同工。

可扩展 Merge Function

基于 Apache Amoro Mixed Format，支持 Replace / Partial Update / Aggregation 等合并模式（实时打宽、预聚合），并在原生 Spark 语法上扩展 Primary Key 定义——与 Paimon 的 merge engine 体系高度对标。

智能数据优化

管理端提供自动调度：小文件合并、过期 snapshot 清理、孤儿文件清理 + 统计信息构建与索引服务，默认 TTL 7 天，加速分析。

兼容与治理

完整支持 Iceberg V2 的 time travel、upsert，遵循 Iceberg REST API 规范，可用原生 Iceberg Client 读写；腾讯云也在向 Apache 社区开源回馈（已贡献 110+ PR）。

改进点TC Iceberg对标 Paimon 特性
Base / Change 双表增量与存量分离，后台合并近似 Paimon 的 LSM 分层（sorted run → compaction）
CDC 流式消费Change Store + 流式增量读高度对应 Paimon 原生 changelog（+I/-U/+U/-D）
按主键自动分桶同桶才需合并，减少 shuffle对应 Paimon 的 bucket + 同键同桶路由
Merge FunctionReplace / Partial Update / Aggregation对应 Paimon merge engine（dedup / partial-update / aggregation）
智能数据优化小文件合并 / snapshot 清理 / 索引对应 Paimon 的 compaction + Tag + 索引能力

结论：是否存在「引进 Paimon」？

TC Iceberg 并非直接移植 Paimon 代码，底层仍是 Iceberg 表格式（Insert / Position-Delete File），与 Paimon 的物理 LSM-tree 实现不同。但从**设计思想**上看，它确实「补齐」了 Iceberg 缺失的实时能力，且方向与 Paimon 高度一致——双表分层、流式 changelog、自动分桶合并、可插拔 merge function，几乎就是 Paimon 核心卖点的「Iceberg 生态化复刻」。因此可以说：TC Iceberg 是在 Iceberg 上借鉴并落实了 Paimon 的核心理念，把 Paimon 这类流式湖格式的优势带回了 Iceberg 的多引擎世界。

一张表定选型

决策维度选 Paimon选 Iceberg
更新频率高频 CDC / 实时 UPSERT低频更新或纯追加
主力引擎FlinkSpark / Trino / DuckDB / Snowflake 等
实时性秒级 / 亚秒级分钟级 / 小时级

治理与生态较弱（持续增强）强，工具丰富

运维重点LSM compaction 与 bucket 调优metadata 快照治理与 delete 文件

选型一句话

Paimon 适合 Flink 生态、实时 CDC、主键高频更新、流式聚合与实时物化视图；Iceberg 适合多引擎分析、大规模离线湖仓、跨团队共享与合规审计。既有实时又有离线分析的团队，可组合为 Paimon 实时层 + Iceberg 分析层 的双湖架构——而 TC Iceberg 则为「坚持 Iceberg 生态」的团队提供了补齐准实时能力的另一条路。
